## 插件回归与缺陷

P1：0.23.1在执行验证命令之后才审批写台账，导致命令先运行且未收到批准模式。回归测试先复现“审批服务不可用却已调用一次shell”，修复后拒绝、取消、审批不可用、非法参数均不运行命令或改台账；verify与skill_result批准顺序、请求上下文、单次权限和回执写入不重复审批均受断言保护。

P2：随包提交规则要求模块名，而引擎要求任务id，R02实际出现两次格式拒绝。规则及手册改为当前任务id和status.commit.label；R03未再出现该格式错误。

源码构建、host/client类型检查、126项P0和37项node:test回归通过；候选包干净安装、入口导入、客户端注册、包内测试及CLI语法验证通过。源码测试明细见[自动化测试明细](自动化测试明细.md)。最终0.23.2的 `npm run verify:package` 由用户在插件源码目录执行并确认通过；此项依据用户执行反馈，观察者没有独立保存该次终端日志。发布版本与远端提交另外核对，不以本报告代替发布成功回执。

## 能力边界与未覆盖范围

`dev_task`对阶段、证据和提交登记实施门禁，通用文件写入不会逐次经过状态机；R03实际在实施项仍为todo时写入文件，随后才逐项审核和标记done。没有安装提交钩子时，不能据此宣称插件能阻止直接shell绕过提交预检。本轮未测试强行篡改台账、直接Git绕过、多人并发、QMS集成、全部Harness/模型版本或生产部署。

scope_hash只覆盖任务files的内容，不能证明命令或范围外业务文件未变；观察者已纠正DSH一次过度解读。模型报告也可能出现测试分类计数错误，必须复核实际日志。自动化中的模拟宿主与真实DSH会话分开计证，不互相替代。
