版本状态

本手册描述自适应流程、项目 Skill/Rule 初始化与可选 SonarQube 审核。可复用 CI 结果、上传式本机扫描，也可在未提交工作区运行本地规则审核；新代码范围由参考分支确定。

本手册替换了旧版 HTML 说明。旧任务快照仍可读，工作台已移除旧版流程页。历史操作保存在历史手册，现行技术细节见自适应流程说明。

开始使用

  1. 在使用的 Web profile 中启用插件，重启 Harness Web。
  2. 进入「工程任务」工作台并选择项目工作区。「自适应流程」用于查看四档路径、给元技能挂载项目 Skill，以及设置可选 SonarQube。
  3. 新建「工程化开发引擎」会话并描述需求。模型先分析复杂度，用 dev_task assess 预览，再在创建任务时给出 complexity 和理由。
  4. 在「任务台账」查看阶段、验证、审核及 Sonar 记录。每个任务独立选择流程；同一项目里的其他会话不会被统一推入同一流程。

台账中的实施项按实现先后执行。“已开始”只记录该项进入开发，当前会话可以直接完成，无需派给其他开发者；“待审查”表示该实施项还没有规格与质量审查记录，它与最后的整项代码审核阶段不同。已完成或已有实施/审查记录的项，在重排列表时会保留。高、超高任务离开任务编排前，实施项 ID 必须与计划中逐行列出的 ID 一致。

工作台「项目初始化」页分开显示项目 Skill/Rule 初始化与 AGENTS.md 生成。前者可复制请求到工程化开发引擎会话，再由 dev_task init_project 执行；页面本身不会直接生成项目 Skill/Rule。

四档任务流程

档次适用情况阶段顺序
低边界明确的局部修改代码开发 → 测试 → 代码审核 → 完成
中常规功能或缺陷修复需求分析 → 代码开发 → 测试 → 代码审核 → 完成
高跨模块且存在实现先后依赖需求分析 → 任务编排 → 代码开发 → 测试 → 代码审核 → 完成
超高完整新模块或大范围重构需求分析 → 架构设计 → 任务编排 → 代码开发 → 测试 → 代码审核 → 完成

高档的任务编排按实现先后拆解，记录依赖和交接产物，不按人员分工。风险级别与复杂度分开判断。阶段顺序和门禁在任务创建时冻结，Skill/Rule 正文更新后会在下一次读取时生效并提示漂移。

元技能、Skill 与 Rule

内置六个通用元技能：需求分析、架构设计、任务编排、代码开发、测试、代码审核。每个阶段加载同名核心 Skill；使用者可为阶段增加项目 Skill。每个 Skill 的 profile.json 保存它引用的 Rule 和证据要求。

同名 Skill 的选择顺序是 .dsh/skills → .agents/skills → 用户目录 → 插件内置。项目同名 Skill 采用自己的 Rule，不混合用户级同名 Skill 的规则。点击“配置核心 Skill 的 Rule”即可编辑；若当前是内置或用户级 Skill，保存时先复制为同名项目 Skill，再写入规则档案。

{
  "meta_bindings": {
    "requirements-analysis": ["my-project-map"],
    "code-development": ["my-project-map", "my-code-backend"]
  }
}

这个配置位于项目根目录 .dsh/meta.json，只增加技能挂载；四档流程由每个任务自己的复杂度决定。

项目初始化

从「自适应流程」页顶部点击「初始化项目 Skill / Rule」，或直接进入「项目初始化」页。点击「复制初始化请求」，在项目根工作区的新「工程化开发引擎」会话中粘贴发送。此页下方的 AGENTS.md 生成是另一项独立功能。

在项目工作区用 dev_task init_project phase=inspect 扫描目录和常见构建清单，取得项目结构、技术栈及可证实版本。扫描结果只提供证据和建议名称；模型再检查代表性源码，拟定项目地图、技术栈、后端或前端开发等 Skill 与 Rule。项目地图应总结整个仓库，供不同需求复用；当前需求的专属调用链与方案应写入任务产物或单独的领域 Skill。phase=propose 会检查草稿是否覆盖扫描发现的主要模块和构建清单；应用前仍需审阅职责、依赖与事实。

  1. phase=inspect：只读扫描并返回建议。
  2. phase=propose：预览拟写入的资源及挂载关系。
  3. phase=apply：使用相同草稿与哈希写入项目目录；已有同名文件不会被覆盖。

应用结果会列出团队配置文件。需要在团队中复用时，将 .dsh/skills/、.dsh/rules/ 与 .dsh/meta.json 纳入 Git；任务审核报告可以继续留在本地。

可选 SonarQube 审核

不使用：「自适应流程」中的 SonarQube 开关保持关闭，或不在 .dsh/meta.json 写 sonar。不需要 Sonar 服务、Token 或扫描任务；代码审核仍按审核元技能及项目 Rule 进行。

使用 SonarQube：打开开关，填写 SonarQube 地址、项目 Key、扫描来源和分析对象，保存配置。Token 可在同页单独输入并保存到 DSH 本机凭据存储，按项目工作区隔离，重启后仍可用；页面只显示是否已配置，不回显值。原有的 Token 环境变量仍可作为后备来源。新建任务会冻结该选项，已建任务不会被自动修改。

{
  "sonar": {
    "enabled": true,
    "host_url": "https://sonarqube.example.com",
    "project_key": "my-project",
    "mode": "branch",
    "source": "ide-local",
    "reference_branch": "main",
    "token_env": "SONAR_TOKEN"
  }
}

Token 不写入项目仓库、任务台账，也不会在页面回显。DSH 的本地凭据是当前操作系统用户可读的本机文件，不能隔离同一用户运行的其他程序。功能验证通过后，在「代码审核」阶段调用 dev_task sonar_check。本地规则审核（ide-local）：从项目 Quality Profile 同步可本地运行的规则，只审核当前任务登记文件中相对 Git 参考分支新增的 Java、JS/TS、Vue、CSS、HTML 和 XML 代码；无需 ceTaskId、提交或推送，审核通过后再提交。CI 结果（ci）：测试后提交并推送，从 report-task.txt 取 ceTaskId。上传式本机扫描（local）：测试后提交，本机运行扫描器并上传分析，无需推送；要求 Developer Edition 或更高版本。后两种方式仅用新代码问题和 new_* Gate 条件阻断；本地规则审核用本地中高级问题和未覆盖文件作为门禁，不代表服务端 Quality Gate。

本地规则审核需要在 DSH 服务进程配置 DSH_SONARLINT_JAVA、DSH_SONARLINT_LIB 和 DSH_SONARLINT_PLUGINS，分别指向 Java 运行时、SonarLint 后台 JAR 目录和内置分析器 JAR；Windows 多个插件路径以分号分隔。JS/TS、Vue 和 CSS 分析还需要本机 Node.js。其他语言文件只有在该项目的服务端 Quality Profile 存在生效规则、本地却无法分析时才列为未覆盖并阻止审核；QMS 项目目前没有 SQL 语言的 Quality Profile，SQL 迁移文件仍需单独数据库验证。部分服务端规则无法在本地执行，完整 Quality Gate 仍需 CI 扫描。

Quality Profile 决定规则，CI 扫描配置决定分析范围。本地规则审核可在项目配置的 sonar.include_paths 中逐行填写后端目录或文件，与 CI 范围对齐；留空时分析任务登记的全部代码。QMS 当前服务端分析索引只有后端 Java 和 XML 文件。

审核结果可在当前项目工作台的「任务台账」中展开“最近一次 SonarQube 审核”查看：包含通过状态、阻断数量、规则、严重程度和文件行号。每次 sonar_check 还会在项目 .dsh/reviews/<任务 ID>/ 生成 Markdown 审核文件；结构化记录保存在 .dsh/task-<任务 ID>.json，不包含 Token。可以把报告目录加入项目 .gitignore。代码或 Skill/Rule 变更后须重新测试和审核；旧记录只代表当时的结果。

sonar_check 和 status 会列出尚未沉淀的阻断案例。失败问题可用 dev_task learn_rule phase=propose 生成项目 Rule 草稿，人工核对是真实且可复用的问题后，再用 phase=apply 挂到项目代码 Skill。误报或一次性问题不会自动变成永久团队规范。

分支与提交的关系

CI 和上传式扫描把结果保存在 SonarQube 的分支或合并请求下，因此需要提交并按目标查询。本地规则审核只使用 Git 参考分支计算新增行，不在 Sonar 服务端创建分支分析。它可以在首次提交之前运行，适用于 Community Build。

上传式本机扫描需要本机扫描器和构建环境、SonarQube Server Developer Edition 或更高版本，并已分析参考分支；Community Build 会在上传前拒绝。本地规则审核使用独立 SonarLint 后台运行服务端 Quality Profile 可支持的规则，无需打开 IDEA。

本地规则审核当前覆盖 Java、常见前端与 XML 差异，无法替代服务端 Quality Gate；如需与服务端规则执行结果完全一致，仍需使用 CI 扫描。

参考：SonarQube for IntelliJ 规则与 Connected Mode、SonarQube Server 的本地分析说明。

验证边界

  • 本地规则审核已在 QMS 真实 SonarQube 项目用未提交的需求代码走到 dev_task sonar_check，发现中高级问题并正确阻止审核通过；SQL 迁移与安装包端到端验证仍待完成。
  • 服务端扫描的新代码问题列表取自查询时的目标分支或请求；同一目标并发扫描时，应使用当前扫描的 ceTaskId 重新核对。
  • 本地钩子与任务门禁只约束受控操作；远程合并、发布以及组织级 CI 策略由项目自行管理。
