版本状态

本手册描述 0.29.3 的自适应流程、项目 Skill/Rule 初始化与可选 SonarQube CI 接入。Sonar 审核当前需要先提交并完成 CI 扫描，尚不支持未提交代码的本地 Sonar 审核。

本手册替换了旧版 HTML 说明。旧任务快照仍可读，工作台已移除旧版流程页。历史操作保存在历史手册，现行技术细节见自适应流程说明。

开始使用

  1. 在使用的 Web profile 中启用插件，重启 Harness Web。
  2. 进入「工程任务」工作台并选择项目工作区。「自适应流程」用于查看四档路径、给元技能挂载项目 Skill，以及设置可选 SonarQube。
  3. 新建「工程化开发引擎」会话并描述需求。模型先分析复杂度，用 dev_task assess 预览，再在创建任务时给出 complexity 和理由。
  4. 在「任务台账」查看阶段、验证、审核及 Sonar 记录。每个任务独立选择流程；同一项目里的其他会话不会被统一推入同一流程。

工作台「项目初始化」页分开显示项目 Skill/Rule 初始化与 AGENTS.md 生成。前者可复制请求到工程化开发引擎会话，再由 dev_task init_project 执行；页面本身不会直接生成项目 Skill/Rule。

四档任务流程

档次适用情况阶段顺序
低边界明确的局部修改代码开发 → 测试 → 代码审核 → 完成
中常规功能或缺陷修复需求分析 → 代码开发 → 测试 → 代码审核 → 完成
高跨模块且存在实现先后依赖需求分析 → 任务编排 → 代码开发 → 测试 → 代码审核 → 完成
超高完整新模块或大范围重构需求分析 → 架构设计 → 任务编排 → 代码开发 → 测试 → 代码审核 → 完成

高档的任务编排按实现先后拆解，记录依赖和交接产物，不按人员分工。风险级别与复杂度分开判断。阶段顺序和门禁在任务创建时冻结，Skill/Rule 正文更新后会在下一次读取时生效并提示漂移。

元技能、Skill 与 Rule

内置六个通用元技能：需求分析、架构设计、任务编排、代码开发、测试、代码审核。每个阶段加载同名核心 Skill；使用者可为阶段增加项目 Skill。每个 Skill 的 profile.json 保存它引用的 Rule 和证据要求。

同名 Skill 的选择顺序是 .dsh/skills → .agents/skills → 用户目录 → 插件内置。项目同名 Skill 采用自己的 Rule，不混合用户级同名 Skill 的规则。点击“配置核心 Skill 的 Rule”即可编辑；若当前是内置或用户级 Skill，保存时先复制为同名项目 Skill，再写入规则档案。

{
  "meta_bindings": {
    "requirements-analysis": ["my-project-map"],
    "code-development": ["my-project-map", "my-code-backend"]
  }
}

这个配置位于项目根目录 .dsh/meta.json，只增加技能挂载；四档流程由每个任务自己的复杂度决定。

项目初始化

从「自适应流程」页顶部点击「初始化项目 Skill / Rule」，或直接进入「项目初始化」页。点击「复制初始化请求」，在项目根工作区的新「工程化开发引擎」会话中粘贴发送。此页下方的 AGENTS.md 生成是另一项独立功能。

在项目工作区用 dev_task init_project phase=inspect 扫描目录和常见构建清单，取得项目结构、技术栈及可证实版本。模型再检查代表性源码，拟定项目地图、技术栈、后端或前端开发等 Skill 与 Rule。

  1. phase=inspect：只读扫描并返回建议。
  2. phase=propose：预览拟写入的资源及挂载关系。
  3. phase=apply：使用相同草稿与哈希写入项目目录；已有同名文件不会被覆盖。

可选 SonarQube 审核

不使用：「自适应流程」中的 SonarQube 开关保持关闭，或不在 .dsh/meta.json 写 sonar。不需要 Sonar 服务、Token 或扫描任务；代码审核仍按审核元技能及项目 Rule 进行。

使用当前 CI 接入：打开开关，填写 SonarQube 地址、项目 Key、分析对象（分支或合并请求）和 Token 环境变量名，保存配置。把 Token 只放在运行插件的服务进程环境变量中。新建任务会冻结该选项，已建任务不会被自动修改。

{
  "sonar": {
    "enabled": true,
    "host_url": "https://sonarqube.example.com",
    "project_key": "my-project",
    "mode": "branch",
    "token_env": "SONAR_TOKEN"
  }
}

功能验证通过后，当前实现要求在「测试」阶段提交并推送，再等待现有 CI 的 Sonar 扫描完成。从该次扫描的 report-task.txt 取得 ceTaskId；到「代码审核」阶段调用 dev_task sonar_check。合并请求模式还需提供请求编号。插件查询该次分析的 Quality Gate 与目标分支或请求的新代码问题；Gate 不通过或存在中高等级问题时阻止审核通过。修复后重新测试、扫描和审核。

失败问题可用 dev_task learn_rule phase=propose 生成项目 Rule 草稿，人工核对可复用原因后再用 phase=apply 挂到项目代码 Skill。一次问题不会自动变成永久团队规范。

为什么当前实现与分支、提交有关？

SonarQube 服务端按项目以及分支或合并请求保存分析结果，所以插件需要用分析对象查询正确的结果。分支是服务端结果的定位信息，并不意味着审核本身必须先提交。

当前插件采用「复用 CI 扫描」的实现：CI 通常扫描已推送的提交，所以当前流程先提交后读取结果。这是本版接入方式的限制。SonarQube for IDE 的 Connected Mode 可以在本地未提交代码上应用服务端 Quality Profile 的部分规则，但它的本地分析不等于完整服务端 Quality Gate；本插件当前没有接入这种本地分析。

如果团队要求「功能通过 → 未提交代码审核 → 修复 → 审核通过 → 再提交」，当前 Sonar 接入还不满足这一顺序。不要把本版 CI 检查描述为提交前 Sonar 审核。

参考：SonarQube for IntelliJ 规则与 Connected Mode、SonarQube Server 的本地分析说明。

验证边界

  • 本版已通过构建、自动化测试和安装包黑盒验证；尚未在真实 SonarQube 实例上完成端到端联调。
  • 服务端扫描的新代码问题列表取自查询时的目标分支或请求；同一目标并发扫描时，应使用当前扫描的 ceTaskId 重新核对。
  • 本地钩子与任务门禁只约束受控操作；远程合并、发布以及组织级 CI 策略由项目自行管理。
