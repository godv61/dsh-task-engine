# 0.23.1：真实项目回归后的流程修复

[← 文档导航](README.md)

本版集中修复真实开发中暴露的资源来源、技能执行、审核记录、验证与提交问题，并改善错误提示。仍使用三个预设流程，不包含自定义流程编排。

## 问题与处理

| 问题 | 处理方法 | 约束性质 |
| --- | --- | --- |
| 项目与个人同名技能被覆盖，界面来源误标 | 管理目录保留全部来源，绑定按名称去重；项目同名规则优先于个人规则 | 代码修复；技能正文最终解析由 Harness 负责 |
| Windows 的 BOM/CRLF 导致内置技能加载失败 | 技能注册、列表和正文读取兼容两种格式 | 代码修复及安装包测试 |
| 技能只披露而不执行，终态技能来不及参与验收 | 新任务检查成功的 skill 工具事件；附加技能登记真实命令回执；终态绑定在进入完成前执行 | 流转和提交门禁 |
| 内置技能被误当附加技能，重复登记导致多余阻塞 | status 列出 command_receipts_required；可选内置回执不升级为额外门禁 | 代码修复 |
| 更新实施项丢失审核；模型重写旧标题使审核消失 | 同 ID/标题保留审核，已有项可省略标题；已审核项改名须明确重开 | 写入前校验 |
| 子代理开工后任务项仍显示待办 | dispatch 提前登记并激活唯一进行项；重派清除旧审核 | 计划记录，不能证明子代理实际执行 |
| 验证未继承调用会话的权限与取消状态 | 验证传递会话沙箱策略、取消信号，保存退出码、超时和沙箱结果 | 代码修复 |
| 审核后错过提交窗口，完成缺少实际 Git 证据 | 新标准流程 v2 审核后提交；核对真实 HEAD、摘要及文件，回写哈希后完成 | 新任务门禁 |
| 文件变化后仍沿用旧测试结论 | 回执关联声明文件摘要，变化后重验 | 流转和提交门禁 |
| status 显示允许提交，实际被过期回执拒绝 | status.commit.allowed 同时检查技能与回执，evidence_blockers 列出过期原因 | 状态与执行校验一致 |
| 模型发明记录字段，需求写入被拒绝 | status.artifact_requirements 主动列出当前阶段允许字段和缺项；错误附恢复说明且不保存 | 保持严格校验，改善可发现性 |
| 小修正也强制派子代理，失败后重复换命令试探 | 小修正允许主代理实施，仍需审核与验证；权限拒绝走正式审批或报告阻塞 | 技能指引，不是硬拦截 |
| 猜测接口字段、混淆模拟测试与真实联调 | 设计核对原始契约与实际组件；报告区分对象、执行状态及证据来源 | 技能指引和人工审核 |

## 新的状态信息

标准流程在需求阶段返回的字段提示示例：

```json
{
  "artifact_requirements": [
    {
      "id": "requirement",
      "name": "需求说明",
      "fields": ["scope", "acceptance_criteria"],
      "missing_fields": ["scope", "acceptance_criteria"]
    }
  ]
}
```

字段来自任务冻结流程，不硬编码同一套字段给所有预设。例如敏捷流程只有 scope；疑问和技术取舍写在已有字段正文，不增加字段名。无记录要求的阶段返回空列表。查询不会更改台账。

`legal_next` 是流程图中的候选去向，不表示门禁已经通过。`commit.allowed` 是阶段、技能和回执层面的提交资格；实际 commit 仍会检查此次输入的文件范围、摘要及所回写的 Git 证据。

## 验证结果与边界

自动化及安装包结果见 [0.23.1 测试说明](testing/0.23.1/测试报告.md)。候选版 rc.3 在一项真实需求中完成了需求/方案审批、8个实施项双阶段审核、测试技能执行、真实验证和本地提交回写。rc.5 与本次字段提示修复有定向回归及包验证，未再次执行整轮真实需求。

该实机过程包含观察方纠正契约、复现异步缺陷和修订报告的干预，不能称为完全自主交付。业务结构树真实联调仍有环境与请求差异待核实，不能用插件本地闭环证明业务端到端可用。

以下问题不由本版解决：Harness 内的文件删除权限限制、同步子代理反馈传播、模型服务鉴权/额度、旧业务项目的 Node/webpack 和测试运行器兼容问题。插件保留失败证据并指导正式恢复，不修改宿主权限系统或模型凭证。

命令退出码成功不证明覆盖充分；本地记录不是防篡改存储；声明文件摘要不涵盖数据库、远程服务和未声明文件。报告准确性与代码质量仍需审核。

## 升级与后续重跑

升级安装后重启 Harness。既有任务沿用冻结流程及原执行约定，不自动迁移到新标准流程；新的执行证据门禁用于带 execution_version=1 的任务。需要比较插件效果时，归档上一轮任务和业务差异，在独立测试项目中将本需求改动恢复到同一基线，再用新会话完整重跑。保留插件修复及历轮证据，不能为重跑无差别清理用户文件。
