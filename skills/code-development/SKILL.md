# 代码开发元技能

仅用户已要求实施时进入本技能。新 intent=implementation 契约中，主会话直接实现无需额外 dispatch；验证仍使用真实 verify 回执，随后 accept_item 原子记录需求/质量审核并标 done。需要委派时必须有明确 delegation_benefit，并按执行计划 dispatch；风险要求的独立审核照常执行。旧任务仍用原来的 dispatch、review_item 和 items。

先读取当前阶段实际绑定的 Skill 和 Rule；没有项目扩展时，依据本元技能、任务产物与源码直接开发。按任务先后顺序修改代码，遵守已有接口和技术栈约束。每个实施项完成时记录结果及对应审核；不要为了分发给多个开发者而拆项。发现需求或方案发生变化时使用 `revise` 回到相应阶段。

交接给测试：变更文件、实现要点、验收场景及已知限制。SonarQube 若启用，在代码审核阶段运行，不在每次编辑时触发。

实施项按完整验收单位拆分，包含实现及其必要回归测试。例如“后端条件与后端测试”“前端字段与前端测试”；整体联调可放在测试阶段。本项测试在本项 done 前编写和执行，不另建一个依赖本项 done 的必要单测项。

新任务先用 `plan_verification` 声明所有必要测试组：`verification_group` 是稳定 ID，`command` 是实际测试命令，`files` 包含生产代码、对应测试及相关构建/配置输入，`item_ids` 关联本组验证的实施项。每个交付文件和实施项都要被覆盖。例：`{"operation":"plan_verification","verification_group":"frontend","item_ids":["FE"],"files":["src/form.vue","tests/form.test.js","package.json","package-lock.json"],"command":"npm test"}`。按项目实际路径和命令填写；覆盖关系须经审核，测试数和哈希不证明测试充分。

运行 `verify verification_group=frontend` 会执行已声明命令并保存独立回执。返回的 `group_result.status` 是本组结果，`task_verified` 和兼容字段 `ok` 是任务整体结果；本组 passed、其它组待运行时，可以先验收本项，不能因此重跑已通过的组。全部必要组有效才可进入任务级审核。同组最新失败不能用旧通过覆盖；修改测试命令须先更新计划。

每个实施项依次执行：`dispatch` → 实现与验证 → `review_item` → 用 `items` 将该项设为 `done` → 派发下一项。`review_item` 只记录规格和质量结论，审核通过后状态仍可为 `doing`；不要把“审核通过”当成“实施项已完成”。发现另有 `doing` 项时先查看其状态并完成或暂停，不绕过单项执行门禁。

暂停用 `items` 将该项设为 `todo`，保留开始记录。修改已审核代码时，用 `revise revision_kind=defect affected_items=[...] target_stage=代码开发` 回到实现阶段；已经处于开发阶段时也可以原地登记缺陷返工。共享交付文件、变化的共同输入和下游依赖会扩大失效范围。影响未知时省略 affected_items，完整返工。未受影响的实现、测试和审核可保留，不为刷新证据重复派发。需求或方案变化使用相应 revision_kind。返回错误后先读具体阻塞和 status.actionable_operations，不跨目录搜索插件实现来猜操作。

执行前检查 `status.execution_planning`、`subagent_capabilities` 和每项 `execution_plan`。低/中档没有任务编排阶段，也必须在代码开发开始时完成策略判断：用 `plan_execution` 记录 `item_id`、`task_boundary`、任务范围内的 `files`、具体 `acceptance`、依赖 `depends_on` 和 `execution_reason`。默认省略 `execution`，不要等用户说“用子代理”。局部小改为 local；可用清晰接口、文件范围和验收交接的独立交付项为 independent；无法脱离当前联动细节的工作为 coupled。引擎自动选择主会话、独立上下文子代理或明确需要历史的子代理。仅因存在前置依赖不应归为 coupled；先完成依赖再委派。用户明确要求全程主会话时，创建任务传 `execution_policy=main_only`，并解释原因，不自行假设该偏好。

派发时只需 `dispatch item_id=...`，引擎读取计划决定实际方式，禁止绕过计划直接调用宿主原生 subagent 工具。主会话执行项由你实现；子代理执行项由工具启动和等待，返回后由你核对交付及运行真实 `verify`。若 `execution_plan.review=independent`，必须先 `review_dispatch` 启动只读独立审核代理；主代理核对其规格/质量结论，再通过 `review_item` 接受相同结论。审核失败须修复、重测、重审，不能用父会话自报 pass 覆盖；相同代码的重复审核有次数限制。最后再用 `items` 标 done。独立审核不代替真实命令验证。

`plan_execution.files` 表示本项允许修改并负责交付的文件；`plan_verification.files` 表示测试依赖的全部输入。只读取且不修改的 package.json、锁文件、构建配置应放在测试输入中，不必加到任务交付 scope 或每项执行范围。配置实际需要修改时才登记其交付归属。将同一交付文件登记给多个项，表示这些项共同维护它，返工会保守地一起重新验收；只读共同输入未变化时可以保留其它项的证据。

删除/重命名必须在改动前给 plan_execution 传 changes：`{path,kind:"delete"}` 或 `{path,kind:"rename",to}`；旧路径及目标仍保留在任务与实施项 files。引擎保存可核验的 Git/已有未提交文本快照，独立审核须读完这些快照及现有交付文件。不要删除快照或把已删路径移出范围来绕过审核。发现需要提高风险时调用 set_risk，再按 status 中更新的审核策略重新验收；旧 done/审核接受会失效，未变实现和真实测试回执可继续复用。

旧任务没有执行策略时，`dispatch` 仍默认由当前代理直接实施，也可以显式选择 spawn/fork。新任务始终按已记录的计划执行，显式参数不能与计划冲突。委派交接必须包含目标、允许修改的文件、验收条件和交接要求。工程引擎保存宿主返回的运行 ID 与结果；子代理完成后，主代理仍须核对文件、运行真实验证及计划要求的独立审核，再执行 `review_item` 并将实施项标为完成。失败不得填写通过；中断后先检查宿主子代理状态，确认已停止再用 `recover_dispatch` 恢复待办。不要把台账中的开始记录或子代理自报完成当成真实验证。

该委派按实施项顺序执行，适合边界明确、需要独立上下文的工作。简单修改默认直接实施，不为使用子代理而拆项。独立不等于值得委派：很短、接口清楚且当前会话可直接验证的独立项，可在 plan_execution 显式选择 direct，并在 execution_reason 说明委派收益不足；高复杂度/高风险项仍遵守独立审核计划。所有任务交付文件须归属到至少一个实施项计划，包括对应测试；派发前补齐遗漏。done 前必须有当前真实测试和有效逐项审核，主会话执行也不能先标完成后补审核。

独立审核核对模型实际收到的全部行内容；有截断或缺页时须补读，路径读取记录不能替代全文覆盖。宿主对长单行截断且无法补读时审核会明确失败，需调整读取上限后重试；不要填写通过。启动失败、取消或证据不完整不消耗有效结论额度；同一代码和审核上下文的重复有效结论仍有上限。重审会退回 doing，接受新结论后再标 done。委派执行期间不可改写父任务台账；释放失败时也必须先恢复。恢复会检查该运行及其后代，宿主查询不支持或记录不可读时不得手改 JSON 解锁。

有可用代码索引时可辅助查询受影响的符号和调用方，并用实际代码核对结果；索引过期或不可用时直接搜索源码。按已确认的需求和任务清单实现；外部规格若被本任务引用，也须核对其版本和来源。索引和外部规格均不能替代当前任务的产物、规则及真实测试。
