# 测试元技能

验证计划的 files 应列出具体生产代码、测试和相关配置文件，不能填包目录或通配符；尚未创建的文件允许预先登记。遇到 INVALID_FILE_SCOPE 时先修正所指的任务或验证组路径，多个坏组可逐个重新登记；目录内代码不能靠“忽略目录”取得有效测试回执。

根据验收条件选择场景，运行真实测试命令，并通过 `dev_task verify` 保存回执。构建可作为辅助检查，但仅编译或跳过测试的命令不能作为测试组计划。失败时先修复再重新运行；测试范围应覆盖本次改动及其主要回归风险。

先查看 status.verification_planning 的各组状态，只对缺失、失败或输入已变化的组执行 `verify verification_group=...`。开发阶段已通过且输入未变的回执可直接用于本阶段；不因阶段切换重跑。每组独立保存真实回执，全部必要组通过且输入指纹有效才可验收。声明 files 时包含生产代码、测试及相关构建/配置；跨项依赖输入由引擎保守纳入。哈希只判断证据是否过期，测试覆盖仍需按验收条件核对。不把已有全局回执追认成多组通过。

`verify` 就是测试执行入口，直接执行并捕获真实结果，不需要先跑一次原生终端。快速检查设置与项目相称的 `timeout_ms`，允许 1000～600000 毫秒，默认 10 分钟；超时如实保留为失败。原生终端中与已登记组完全相同的命令会被引导到该组，其他诊断命令仍可使用。

环境阻塞时按 verify.recovery 保留原测试和辅助程序，只为确切命令申请一次执行批准，不改 ACL 或整场会话权限。页面需求区分资源冒烟、业务逻辑与浏览器行为验证；静态资源可访问不能代替对重复提交、身份切换、冲突反馈等验收条件的验证。

提交时点以 status.commit.checkpoints 和 next_action 为准，不假设所有流程都在本阶段提交。使用 commit 返回的 record_call，在实际 Git 提交后回填真实 HEAD hash，保持 message 和 files 一致。

NO_TEST_SUMMARY 表示没有可识别的非零测试摘要；使用项目已有的 node:test、Surefire/Failsafe、pytest、Python 标准库 unittest 等实际运行器，不自行打印测试数量。unittest 使用 `python -m unittest discover -s tests -v` 等原生调用，必须有完整的最终摘要；跳过和预期失败不算实际通过，零测试不能放行。环境拒绝、超时和取消应如实记录；按环境恢复指引处理，不为环境问题修改测试隔离、脚手架或会话权限。新一次失败始终优先于同组旧通过。

Maven 测试命令必须在输出中证明 Surefire/Failsafe 至少执行了一个测试；退出码为 0 但测试数为 0 或没有测试摘要时，验证不能通过。构建通过不等于测试通过。必要时调整命令让测试摘要可见，并核对原始测试报告。

交接给代码审核：测试命令、结果、覆盖的场景和未覆盖原因。优先验证业务主入口、条件闸门、外部副作用与失败恢复，不把只有常量、序列化或参数透传的测试说成整条流程已验证。当前计划及输入不变的有效通过记录可保留；缺失/失败/过期才重跑，不为查看日志重复验证，完整回执通过 status detail=true 读取。不要把模型的口头判断当成通过的测试。
