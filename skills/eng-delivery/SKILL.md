# 工程流程编排

`dev_task` 是任务状态、阶段流转与门禁的唯一事实来源。流程预设决定阶段图与守卫；项目配置决定阶段使用哪些技能、每个技能遵守哪些规则，以及产物字段和提交文本。内置业务技能与规则只是可选样本，不能因它们随包安装就推定任务必须使用。

1. 先调用 `dev_task`（operation=status）查找当前工作区和分支的任务；有多个候选时让使用者明确目标。没有任务时按实际需求调用 `create`，已有任务则从返回的 `stage` 继续。
2. 读取 `status.bindings`、`skill_obligations`、`artifact_requirements`、`legal_next` 和 `commit`。只加载当前及即将进入的终态实际绑定的技能，遵守披露的冻结规则正文；没有绑定时不自行补上任何内置技能或规则。
3. 技能要求的证据以其配置和 `status.skill_obligations` 为准：仅对 `command_receipts_required` 列出的技能通过带真实命令的 `skill_result` 记录；`manual` 通过人工审批记录；`artifact`、`review` 与 `none` 按对应阶段操作或无需额外回执处理。不要把所有技能都当成命令型技能。技能加载成功不等于要求的证据已经完成。
4. 需要记录产物时，只使用 `artifact_requirements` 给出的 id 与字段。按当前流程要求完成确认、实施项、验证和审核，再调用 `advance`；被拒绝时按返回的阻塞原因修正，不改任务文件绕过门禁。
5. 只在 `status.commit` 允许的检查点申请提交，并按冻结配置校验文件范围与消息。提交后按工具要求回写真实 Git HEAD。到达终态后调用 `complete`，以其完成条件为准；需要返工时使用 `revise`。

不同流程的阶段数与守卫不同，不把某一预设的阶段顺序、技能映射、规则组合或提交格式当作所有项目的默认工作方法。用户修改配置只影响之后创建的任务；进行中的任务继续遵守创建时冻结的配置与资源。
