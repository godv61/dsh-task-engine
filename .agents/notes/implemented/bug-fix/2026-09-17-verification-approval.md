# Agent Note: 验证命令单次审批

Status: implemented

## Problem

0.23.1 的 verify / skill_result 在执行 shell 后才通过 resolveWriteMode 审批任务文件写入；命令没有收到批准的权限。dshtest 实机中 npm test 的子进程测试经 shell 升级可通过，dev_task 的回执仍为 workspace-write / EPERM，无法完成交付。

## Decision

两类验证操作先验证参数并申请审批，再将批准模式覆盖到本次 shell 请求，同时保留会话工作区、其他策略字段及取消信号；同次回执写入复用审批。默认调用仍传递原会话策略。拒绝、取消、缺少服务或非法参数不启动命令、不写台账；不修改会话常驻模式，不自动重试，不把外部 shell 成功作为插件回执。

## Alternatives considered

**会话级提权。** 修改常驻模式会扩大后续无关命令的权限，超出本次批准范围，因此只覆盖当前请求。

**外部 shell 结果代替插件回执。** 外部测试通过不能证明插件记录的命令、范围和权限，因此仍由工具执行命令并生成真实回执。

## Consequences

审批等待发生在命令执行之前，拒绝不再产生命令副作用；同次验证和台账写入只请求一次批准。权限升级必须具备 host sandboxPolicy 服务。实机提交同时暴露规则把模块名误当任务 id 的文案冲突；规则及手册遵循 status 的提交提示，保留引擎校验。

## Testing

回归用例先复现“无审批服务却执行一次命令”，修复后通过；另覆盖拒绝/取消、非法参数、两类操作批准时机、单次模式、不重复审批及后续调用恢复会话策略。完整实机循环和发布验证结论以测试报告为准。
