# 清单数据与回填约定

## 生成输入

UTF-8 JSON。`task_id` 使用当前任务标识，`revision` 为本轮清单版本，`title` 为给产品看的需求名称。`questions` 至少一项，只填写实际待确认的问题。

```json
{
  "task_id": "EXPENSE-REFUND",
  "revision": "v1",
  "title": "报销单驳回行为待确认 · v1",
  "questions": [
    {
      "kind": "逻辑遗漏",
      "question": "报销单被驳回后，本次填写的明细和附件是否保留？",
      "evidence": "需求说明 3.2 只描述了审核通过；原型的驳回按钮未标注驳回后的数据结果。",
      "need": "请确定驳回后的数据保留规则，供重新提交流程和验收使用。",
      "options": [
        { "title": "保留内容", "text": "驳回后保留明细和附件，申请人修改后重新提交。" },
        { "title": "清空重填", "text": "驳回后清空本次明细和附件，申请人重新填写提交。" }
      ],
      "sources": [
        { "label": "需求说明 3.2", "text": "此处填写实际查到的描述，不能将本示例当作项目事实。" }
      ]
    }
  ]
}
```

`kind` 仅使用模板的五类：`逻辑冲突`、`逻辑遗漏`、`材料不对齐`、`原型与文档冲突`、`其他`。

每题必填 `kind`、`question`、`evidence`、`need`。`options` 为可选的 `{title,text}` 数组；没有明确可选方案时可省略。`recommendation` 是可选建议，仅在没有 `options` 时使用。二者同时提供会被拒绝，避免建议被页面忽略。无建议也无选项时，页面仍支持自由填写。`sources` 是可选的依据对照列表，结构为 `{label,text}`。

示例只说明格式。生成实际清单时必须替换为本次查阅的事实，不向产品发送示例题和虚构材料。

## 模板与版本

DSH 受控入口采用相同的题目结构；把输入中的 `task_id` 改为 `engine_task_id`，保留 `revision`、`title`、`questions`，将其序列化为 `material_template.json`。指定 `identity_field=task_id` 后，插件生成清单标识并写入模板。这个路径无需运行脚本，也不需要计算脚本的 `checklist_hash`；完整文件的文本指纹由插件登记并校验。

脚本保留基线模板的其他字节，只替换 `#card-data`。特殊字符会进行 JSON 嵌入转义，问题文本仍按原文显示。

模板按 `task_id` 缓存填写内容，并以序号识别问题。为防止同一任务改题后串用旧答案，生成后的 `task_id` 是清单标识：`<原任务标识>--<内容指纹>`。指纹由任务、版本、标题和全部问题数据计算；相同内容可继续填写，题目内容或顺序变化后使用新标识。

脚本生成 HTML 的数据还包含 `engine_task_id`、`revision` 和 `checklist_hash`，用于追溯；插件生成的数据包含前两者，文件指纹在材料台账中。它们不会改变模板的界面交互。交回 JSON 中的 `task_id` 应对应清单标识，不能手动改成原任务标识。

## 产品回填

模板导出以下原有结构，不额外要求产品修改 JSON：

```json
{
  "task_id": "EXPENSE-REFUND--由生成器计算的内容指纹",
  "passed_by_card": true,
  "answers": [
    {
      "index": 1,
      "kind": "逻辑遗漏",
      "question": "报销单被驳回后，本次填写的明细和附件是否保留？",
      "choice": "1",
      "choice_title": "保留内容",
      "answer": "保留明细和附件，但驳回原因需要显示在重新提交页面。"
    }
  ]
}
```

`answer` 才是产品最终说法；选项标识和标题只是填写过程信息。结构校验通过后，仍要检查答案的清晰度、冲突和范围变化。

`passed_by_card`、脚本校验结果、选中了“采用建议”都不等于 DSH 最终需求确认。产品填写内容是完善需求总结的输入，后续由当前需求确认流程收集正式批准。
